# Forma — бэкенд, роли, вход по телефону и промокоды (спецификация v0.2, 10 октября 2026)

Дополняет `forma-product-and-backend-plan.md` (шаг 0a). Код каркаса лежит в проекте рядом: `claude/forma-backend/*` (Node.js, PostgreSQL, WebSocket). Он проходит 76 автоматических проверки на настоящем PostgreSQL (PGlite). Пока нигде не развёрнут.

## 1. Роли и вход

В онбординге три варианта:
1. **Тренируюсь сам**: свободный клиент, без тренера.
2. **Тренируюсь с тренером**: клиент вводит публичный код своего тренера (8 символов, выдаёт сервер при активации тренера, например `K7M2QX9A`).
3. **Я тренер**: нужен секретный код доступа. Код выдаёт владелец лично. Вход только после проверки кода.

Два разных кода, их нельзя путать:
| | Код доступа тренера | Код тренера для клиентов |
|---|---|---|
| Пример | секретная фраза, выдаёт владелец | `K7M2QX9A` |
| Кто видит | один человек | все клиенты тренера |
| Что даёт | роль «тренер» | привязку клиента к тренеру с согласием на доступ |
| Хранение | только хеш (scrypt) на сервере | открытый текст в таблице `coaches` |

Что сделано в приложении сейчас (PWA и макет): три роли в онбординге, вход по коду доступа, режим тренера сохраняется между запусками, выход из режима («Клиенты» и Профиль), вход после онбординга («Тренер» → «Я тренер: войти по коду доступа»). Проверка кода пока локальная (PBKDF2, 150 000 итераций, в приложении лежит хеш, а не сам код; 3 ошибки подряд дают паузу 30 секунд, дальше она удваивается). Это временная мера: пока нет сервера, она отделяет тренерский режим от клиента для тестов, но не защищает данные. Реальную защиту даёт только сервер (раздел 3).

## 2. Архитектура

```
Приложение (локальное хранилище, работает офлайн)
   │  POST /v1/sync   (очередь изменений: документы, тренировки, вес; ответ: события после курсора)
   │  WebSocket /v1/ws (живые события)
   ▼
API (Node.js)  ──  PostgreSQL (docs, sessions, weights, links, coach_items, events, audit_log)
   │
   └─ шина событий: сейчас в памяти одного процесса; для нескольких экземпляров LISTEN/NOTIFY или Redis
```

Поток «клиент меняет данные, тренер видит сразу»:
1. Клиент завершил тренировку. Приложение сохраняет её локально и кладёт в очередь.
2. `POST /v1/sync` пишет тренировку (`sessions`, идемпотентно по id) и в той же транзакции создаёт событие `client.updated` для тренера.
3. После коммита сервер отправляет событие в открытые сокеты тренера. В тесте путь занял около 10 мс.
4. Если у тренера приложение было закрыто, событие лежит в таблице `events`. При открытии сокета (`since=<последний id>`) или `GET /v1/events?since=` приходит всё пропущенное.
5. Тренер открывает дашборд: `GET /v1/coach/clients` отдаёт агрегаты (последняя тренировка, 7 и 30 дней, боль за неделю, вес и динамика за 30 дней), `GET /v1/coach/clients/:id` отдаёт карточку с историей.
6. Обратный путь: заметка или программа тренера (`POST /v1/coach/clients/:id/notes|programs`) становится событием клиенту и доставляется так же, онлайн или по курсору.

## 3. Код тренера на сервере

- `POST /v1/coach/claim {code}`: сервер сравнивает с хешами активных кодов (`coach_codes`: scrypt, соль, лимит устройств, срок, отзыв). Совпало: пользователь получает роль `coach` и публичный код приглашения.
- Лимиты: 5 неверных попыток на пользователя за 15 минут, 20 на IP; после лимита даже верный код не принимается до окончания окна. Все попытки пишутся в `audit_log`.
- Регистр важен, пробелы по краям обрезаются. Код от 8 символов (в CLI) для новых кодов.
- Роль читается из базы на каждом запросе, а не из токена: отзыв кода (`node src/cli.js revoke <id>`) закрывает доступ немедленно и закрывает привязки.
- Один код можно привязать к N устройствам (`max_uses`). По умолчанию 1: код выдан одному человеку.
- Выдача кода: `node src/cli.js add "Имя" 1`. Код вводится в терминале, в базе остаётся только хеш.

## 4. API (v0.1)

| Метод | Путь | Кто | Что |
|---|---|---|---|
| POST | /v1/auth/phone/start, /verify | любой | вход по номеру телефона (раздел 8) |
| POST | /v1/redeem | клиент | ввод персонального промокода программы (раздел 7) |
| POST, GET, DELETE, PUT | /v1/coach/codes… | тренер | создание, список, отзыв промокодов, обновление программы |
| POST | /v1/me/backup | авторизован | включить или выключить облачную копию для клиента без тренера |
| POST | /v1/auth/device | любой | аккаунт по случайному id установки, выдаёт токен (60 дней) |
| GET | /v1/me | авторизован | роль, тренер клиента или код приглашения тренера, обновляет токен |
| POST | /v1/coach/claim | клиент | активация роли тренера по секретному коду |
| POST / DELETE | /v1/link | клиент | привязка по коду тренера (нужно `consent:"v1"`) / отзыв |
| POST | /v1/sync | авторизован | отправка документов (`profile, plan, progs, set, nutr`), тренировок, веса; ответ: события после курсора |
| GET | /v1/events?since= | авторизован | события после курсора |
| GET | /v1/coach/clients | тренер | список клиентов с агрегатами |
| GET | /v1/coach/clients/:id | тренер | карточка клиента (profile, plan, история, вес) |
| POST | /v1/coach/clients/:id/notes, /programs | тренер | заметка или программа клиенту |
| DELETE | /v1/coach/clients/:id | тренер | убрать клиента |
| DELETE | /v1/account | авторизован | удаление аккаунта и данных |
| WS | /v1/ws | авторизован | первое сообщение `{t:"auth",token,since}`; события `{t:"event",id,type,payload}` |

События: `client.linked`, `client.updated`, `client.unlinked`, `code.redeemed` (тренеру); `coach.note`, `coach.program`, `coach.removed` (клиенту).

Права: клиент пишет только в свои данные. Тренер читает только клиентов с активной привязкой (`links.status='active'`), каждое чтение карточки пишется в `audit_log`. Питание (`nutr`) тренеру не отдаётся: это открытый вопрос 5 из плана, по умолчанию закрыто.

## 5. Сценарии и подводные камни

Проверено автотестами:
- Неверный код, регистр, блокировка после 5 ошибок, повторный ввод тем же человеком, лимит устройств на код, отозванный код.
- Клиент не вызывает методы тренера (403); тренер не видит чужих клиентов и не пишет им заметки.
- Привязка без согласия отклоняется; код без учёта регистра и с пробелами; повторная привязка к тому же тренеру безопасна; второго тренера без отвязки от первого подключить нельзя; тренер не может быть клиентом.
- Повторная отправка той же тренировки не дублируется и не создаёт лишних событий.
- Конфликт версий профиля: сервер оставляет свою версию и возвращает её приложению.
- Битые данные: неизвестный ключ, кривая дата, нереальный вес, документ больше 200 КБ.
- Обрыв связи: события приходят по курсору, повтор по курсору дубли не даёт.
- Отзыв клиентом, удаление тренером, удаление аккаунта: второй стороне приходит событие, данные закрываются сразу.
- Поддельный токен и сокет без авторизации закрываются.

Известные риски и что с ними делать:
1. **Слабый код.** `Vershinin26` (бренд плюс год) подбирается по словарю. Лимиты на сервере замедляют перебор, но защиты от знающего человека нет. Для кода тренера рекомендую 12+ символов, случайных. Лимит по IP обходится сменой сети, поэтому код надо считать секретом.
2. **Локальная проверка в PWA.** Хеш лежит в публичном репозитории. Подбор слабого кода по хешу возможен офлайн. После запуска сервера локальную проверку убираем и меняем код.
3. **Переустановка стирает установку.** Идентификатор устройства лежит в приложении. Решение принято: вход по номеру телефона (раздел 8). После входа по телефону возвращается прежний аккаунт с ролью, клиентами и привязками. Пока приложение не подключено к серверу, помогает резервная копия данных.
4. **Закрытое приложение не получает сокет.** Для уведомлений нужны push: web push в PWA на iOS 16.4+ только после установки на экран, в нативном приложении APNs (нужен Apple Developer).
5. **Часовые пояса.** Даты тренировок приходят в локальном времени клиента, агрегаты «7 дней» считаются по Москве (`msk_today()`). Для клиентов в других поясах граница недели сдвинута до нескольких часов. Нужно хранить пояс клиента.
6. **Несколько экземпляров сервера.** Список сокетов и лимитер лежат в памяти процесса. До второго экземпляра их надо перенести в Redis или LISTEN/NOTIFY.
7. **Список клиентов.** Сейчас 4 запроса на клиента. Для 50 клиентов приемлемо, дальше нужен один агрегирующий запрос или материализованное представление.
8. **Две активные сессии одного человека.** Последняя запись побеждает (документы), тренировки только добавляются. Возможна потеря правки в профиле при одновременном редактировании на двух устройствах; приложение получает `conflicts` и должно показать выбор.
9. **Программа тренера клиенту уходит копией.** Правка тренера после отправки до клиента не доходит, пока он не отправит новую версию. Нужна версия программы и пометка «обновлено».
10. **Персональные данные.** Сервер должен стоять в России (ФЗ-152). Согласие на доступ тренера `consent v1` хранится в привязке, текст согласия должен быть в приложении и в политике. Уведомление РКН и политика до запуска. Категория «данные о здоровье» требует ответа юриста.
11. **Журнал событий растёт.** Нужна чистка записей старше 90 дней; клиент, не заходивший дольше, делает полную синхронизацию.
12. **Отзыв кода из CLI не шлёт событие онлайн-тренеру.** Доступ закрывается на следующем запросе, открытый сокет закрывается при следующем переподключении. Для мгновенного разрыва нужна команда в самом сервисе.

## 7. Персональные промокоды программ

Идея: тренер придумывает для каждого клиента уникальный код, клиент вводит его в приложении, и программа сама появляется у него в «Мои».

Как работает:
1. Тренер собирает тренировку и создаёт код: `POST /v1/coach/codes {code?, label, program, expiresDays, bindPhone?, autoLink?}`. Код тренер придумывает сам (например `ANNA-LEGS-1`) или нажимает «Сгенерировать» (10 случайных символов). Допустимы 6–24 символа: буквы, цифры, `-`, `_`; регистр не важен. Код уникален среди всех тренеров; занятый даёт 409.
2. Клиент вводит код: `POST /v1/redeem {code}`. Сервер отдаёт копию программы и посылает событие `coach.program` (`source:"code"`). Приложение кладёт её в «Мои» с пометкой источника и версии. Тренеру приходит `code.redeemed` с меткой «Анна, ноги».
3. Код одноразовый, живёт `expiresDays` (по умолчанию 30, максимум 365), тренер может отозвать его до использования.
4. Тренер правит программу: `PUT /v1/coach/codes/:id/program`. Клиент получает новую версию (`ver`) событием. Приложение не должно молча перезаписывать то, что клиент изменил у себя: показывать «Тренер обновил программу» и предлагать принять.
5. Код может быть привязан к номеру телефона клиента (`bindPhone`). Тогда даже угаданный код у чужого человека не сработает (403).
6. Код может сразу подключить клиента к тренеру (`autoLink`). Подключение происходит только если клиент подтвердил согласие (`consent:"v1"`); без согласия программа выдаётся, подключения нет, в ответе `linkNote:"consent_required"`.

Риски и решения:
- **Придуманные коды слабые** (`ANNA` и подобные). Минимум 6 символов, перебор ограничен (8 попыток за 10 минут на пользователя, 40 на IP), код одноразовый. Для личных программ включать `bindPhone`. Кнопка «Сгенерировать» должна быть основным путём.
- **Пересечение кодов разных тренеров.** Ответ 409 «код занят» показывает, что такой код существует. Это допустимая утечка; чтобы её убрать, можно добавлять к коду префикс тренера.
- **Код отправили не тому человеку.** Одноразовость и срок; тренер видит, кто активировал (`client` в списке кодов). Отозвать уже активированный код нельзя: программа остаётся у клиента как его копия.
- **Клиент ввёл код до регистрации.** Аккаунт устройства создаётся сразу, поэтому код можно активировать на первом экране и без телефона. Если код привязан к номеру, приложение сначала просит войти по телефону.
- **Тренер не может быть клиентом**, поэтому свой код ввести не сможет (409).
- **Оплата.** Код можно выдавать после покупки на сайте; тогда webhook оплаты создаёт код автоматически. Это закладывается на шаге оплаты.

В приложении не сделано: экран создания кода у тренера и поле «Ввести код программы» в «Мои». Они подключаются вместе с синхронизацией.

## 8. Вход по номеру телефона (в коде есть, по умолчанию выключен; решение от 10 октября ниже)

- Вход по номеру одноразовым кодом из 6 цифр: `POST /v1/auth/phone/start {phone}`, затем `POST /v1/auth/phone/verify {phone, code}`.
- Номер приводится к формату `+7…` (8 и 10 цифр тоже принимаются). Код живёт 5 минут, 5 попыток, затем сгорает. Хранится только HMAC кода.
- Если гость уже пользовался приложением, номер привязывается к его аккаунту. Если номер уже известен (после переустановки), возвращается прежний аккаунт (`restored:true`): роль тренера, клиенты, привязки, история. Данные с сервера важнее пустых локальных.
- Защита: пауза 60 секунд между отправками, 5 кодов в час на номер, 10 в час на IP, дневной предел отправок на весь сервис (по умолчанию 500) против накрутки платных SMS.
- Для проверки в App Store нужен демо-номер с фиксированным кодом, без отправки SMS (в коде предусмотрен).
- Канал доставки: интерфейс `sms.send(phone, text)`. Рекомендую российского SMS-провайдера как основной канал. Telegram Gateway дешевле (платите только за доставленные), но данные уходят зарубежной компании; до решения юриста по трансграничной передаче не включать. FlashCall по оценке автора статьи доставляется в 50–70% случаев, как единственный канал не годится ([Sostav](https://www.sostav.ru/blogs/289457/87665)).
- Номер телефона это персональные данные. SMS-провайдер становится обработчиком по поручению: указать в политике и договоре.
- Для первого запуска вход по телефону можно сделать необязательным (гостевой режим остаётся), обязательным только для тренера и для клиентов, привязывающихся к тренеру.

## 9. Хостинг: Яндекс Облако

Вывод: подходит, с оговорками.
- Платформа выполняет требования 152-ФЗ на уровне УЗ-1 (аттестация единого сегмента публичного облака, три зоны доступности). Часть требований остаётся на стороне клиента; перечень в соглашении об обработке данных ([Yandex Cloud, 152-ФЗ](https://yandex.cloud/ru/security/standards/152-fz)).
- Есть управляемый PostgreSQL ([документация](https://yandex.cloud/ru/docs/managed-postgresql)), сервер использует обычный PostgreSQL, отдельной адаптации не нужно.
- Облако не делает вас соответствующим закону само по себе: уведомление Роскомнадзора, политика, текст согласия и роли остаются на вас.
- Рекомендуемая схема: одна виртуальная машина или контейнер (Node.js, WebSocket) плюс Managed PostgreSQL в зоне `ru-central1`, резервные копии средствами сервиса, HTTPS, переменные `DATABASE_URL`, `SECRET`.
- Не проверено: тарифы (посмотреть в калькуляторе Яндекса), поддержка долгих WebSocket в бессерверных сервисах (поэтому предлагаю обычную ВМ или контейнер), точные пункты аттестата для вашего уровня защиты данных. Встроенную отправку SMS в Яндекс Облаке я не подтвердил, поэтому закладываю отдельного SMS-провайдера.
- Альтернативы с той же аттестацией: Selectel, VK Cloud. Яндекс выбирайте, если важны удобство и управляемые сервисы.

## 12. Яндекс Облако: лимиты и бесплатный режим (проверено 10 октября 2026)

- **Стартовый грант:** физлицо в РФ не менее 4 000 ₽ на 60 дней; бизнес-аккаунт: 4 000 ₽ при оплате картой, 10 000 ₽ при оплате переводом. Грант выдаётся один раз и только если карта привязана при создании платёжного аккаунта. Не тратится на GPU, Postbox, платную поддержку и Marketplace ([документация](https://yandex.cloud/ru/docs/getting-started/usage-grant)).
- **После окончания пробного периода** (страница для Казахстана, для РФ не проверял): ресурсы приостанавливаются на 60 дней, затем удаляются навсегда, если не перейти на платный тариф ([документация](https://yandex.cloud/ru-kz/docs/getting-started/free-trial/concepts/trial-ending)).
- **Бесплатный уровень (в месяц, не переносится, считается на платёжный аккаунт)** ([документация](https://yandex.cloud/en/docs/billing/concepts/serverless-free-tier)): Cloud Functions 1 млн вызовов и 10 ГБ·ч; Serverless Containers 1 млн вызовов, 10 ГБ·ч памяти, 5 vCPU·ч; API Gateway 100 тыс. запросов; YDB Serverless 1 млн Request Units и 1 ГБ; Object Storage 1 ГБ; Cloud Logging 5 ГБ; исходящий трафик VPC 100 ГБ.
- **Managed PostgreSQL бесплатного уровня не имеет.** Пример из прайса: хост 2 vCPU / 8 ГБ около 5 600 ₽/мес, HDD 3,74 ₽/ГБ/мес, бэкапы бесплатны в пределах объёма хранилища ([прайс](https://yandex.cloud/ru/docs/managed-postgresql/pricing)). Цену минимального хоста не нашёл.
- **ВМ:** страница цен пишет «от $2,85 в месяц», в описании «от $1,50»; точное смотреть в калькуляторе.

Вывод: сервер с PostgreSQL и постоянными WebSocket-соединениями полностью бесплатно в Яндекс Облаке не запустить.
- Serverless Containers дают 5 vCPU·ч в месяц, это около 7 часов работы одного ядра. Контейнер, который держит соединения, работает непрерывно (720 часов в месяц).
- YDB не PostgreSQL, потребуется переписывать слой данных; совместимость с моей схемой не проверена.
- Опрос сервера вместо WebSocket не решает: 100 клиентов с опросом раз в 30 секунд дают около 8,6 млн вызовов в месяц против бесплатного миллиона.

Реалистичный старт: одна небольшая ВМ (Node.js, PostgreSQL и Caddy для HTTPS на одной машине), первые 60 дней покрывает грант, дальше платит владелец; Managed PostgreSQL подключаем, когда появятся реальные клиенты.

## 13. Какие данные хранит сервер (решение: минимум, основная копия на телефоне)

Принцип: основные данные живут на телефоне пользователя. Сервер получает только то, что нужно для связи с тренером.

| Где | Что |
|---|---|
| Только на телефоне | каталог упражнений, календарь и напоминания, настройки, подробный журнал питания (продукты), избранное, черновики |
| На сервере всегда | номер телефона, имя, роль, привязки к тренеру и время согласия, промокоды, события доставки, журнал доступа тренера |
| На сервере, пока есть связь с тренером | профиль (пол, дата рождения, рост, вес, цель, уровень, ограничения), план, программы, история тренировок, вес по датам, итоги питания по дням |
| Не хранится вообще | пароли, сам секретный код тренера, данные карт |

Как это обеспечено в сервере (проверено автотестами):
- Клиент без тренера и без включённой копии: сервер не принимает данные (`403 sync_not_enabled`), на сервере только аккаунт.
- Клиент подключился к тренеру: приложение отправляет накопленное и дальше синхронизируется.
- Связь прервалась (клиент отозвал или тренер убрал): данные клиента с сервера удаляются, если копия не включена. На телефоне всё остаётся и при новой привязке отправляется заново.
- Клиент без тренера может включить облачную копию (`POST /v1/me/backup {on:true}`), тогда данные хранятся и при разрыве связи не удаляются; выключил копию: удаляются.
- Питание: документ ограничен 60 КБ. Приложение отправляет итоги по дням (калории, БЖУ, вода), не журнал продуктов.

Цена решения: у клиента без тренера и без копии потеря или переустановка телефона означает потерю данных. Нужно предупреждать при онбординге и предлагать копию. Для нативного приложения можно добавить копию в iCloud (хранение у Apple, за рубежом, вопрос юристу).

Что это не отменяет: даже небольшой объём данных на сервере остаётся персональными данными, поэтому сервер в России, политика, согласие и уведомление РКН нужны так же.

## 14. Решения от 10 октября 2026 (вход, Telegram, домен)

**Вход и аккаунты, по фазам**
- **Фаза 1 (сейчас): без номеров телефона.** Включён только гостевой аккаунт по идентификатору установки (`POST /v1/auth/device`). Вход по телефону в сервере выключен (`PHONE_AUTH` не задан, эндпоинты отвечают 404). Тренер входит по секретному коду, клиент подключается по коду тренера или промокоду.
- **Фаза 2: вход через Telegram.** Основной канал подтверждения. Если у человека нет Telegram, он остаётся в гостевом режиме (пользовательский режим): приложением и привязкой к тренеру пользоваться можно, но восстановления после переустановки нет. SMS можно добавить позже как запасной канал, если без него будут терять много пользователей.
- Для фазы 2 понадобятся: способ подключения Telegram Gateway из России (напрямую или через агрегатор с договором на ИП; не проверено), решение юриста по передаче номера в Telegram, поле «войти по Telegram» в приложении. Интерфейс отправки кода в сервере уже отделён от остального (`sms.send`), заменяется на адаптер Telegram.

**Последствия фазы 1, которые надо учитывать**
1. Переустановка приложения создаёт новый гостевой аккаунт: роль тренера и привязки клиента теряются.
2. Тренер после переустановки вводит секретный код заново, а один код по умолчанию рассчитан на одно устройство (`max_uses=1`). Свой код нужно создавать с запасом (например 5 устройств).
3. Клиент после переустановки вводит код тренера заново. Его данные на сервере к этому времени уже удалены связью или остались у старого гостевого аккаунта; с телефона уцелеет только то, что он сохранил в резервной копии.
4. До фазы 2 просим тренера и клиентов делать резервную копию данных в приложении.

**Домен**
- Домена нет. Для публичного запуска он нужен: iPhone-приложению нужен HTTPS, а сертификат выдаётся на домен.
- Для тестов можно использовать адрес вида `IP.sslip.io` с автоматическим сертификатом (известный приём, здесь не проверял). Для клиентов нужен свой домен, например `api` на домене вашего сайта.
- Домен регистрируете вы у регистратора на ИП; цену смотрите у регистратора.

## 15. Подключение приложения к серверу (сделано 10 октября 2026)

Модуль `NET` в оболочке приложения (PWA и макет). Включается, только если задан адрес сервера (`localStorage fnet.api`); без адреса приложение работает как раньше, локально. Токен и состояние лежат в ключе `fnet`, вне резервной копии данных.

Что работает (проверено в браузере на двух «телефонах», сервер локальный):
- Гостевой аккаунт по идентификатору установки; токен продлевается, при отказе выдаётся заново.
- Вход тренера по секретному коду через сервер: из онбординга и из «Тренер → Я тренер». Код тренера для клиентов (8 символов) показывается во вкладке «Клиенты». Повторный вход идемпотентен, выход из режима не снимает роль на сервере.
- Клиент вводит код тренера: сервер создаёт привязку с согласием, приложение отправляет профиль, вес и историю тренировок (порциями по 30), дальше отправка через 3 секунды после каждого изменения. Тренер получил историю клиента за 3,6 секунды (из них 3 секунды ожидание перед отправкой).
- Тренер видит клиентов в дашборде (список и 400 дней истории), обновление по событию.
- Заметка тренера доходит до клиента за 0,2 секунды. Программа или одна тренировка тренера появляется у клиента в «Мои» (раздел «От тренера» и отдельные программы), повторная доставка дублей не создаёт.
- Нет сети: клиент ставит статус «нет связи», накопленное уходит при возвращении связи; тренер после перезапуска приложения видит клиентов.
- Клиент отзывает доступ: тренер теряет клиента, данные клиента с сервера удаляются.
- Текст согласия показан в онбординге, в «Тренер» и в профиле.

Не сделано: ввод промокода программы клиентом («Мои») и создание промокода тренером; резервная копия по желанию клиента (переключатель); push-уведомления; восстановление после переустановки; проверка на реальном iPhone и по реальному адресу сервера.

Как запустить локально: `cd forma-backend && npm install && node src/dev.js` (PostgreSQL в памяти, данные пропадают при остановке; тестовый код тренера `Dev-Coach-Code-1`, настоящий код сюда не вписывать). В приложении задать адрес: `localStorage.setItem("fnet.api","http://localhost:8787")`.


## 16. Дашборд тренера v2: питание, рейтинг, корректировка нормы

**Данные.** Клиент отправляет новый документ `nsum` (до 40 КБ): `{norm:{k,p,f,c,adj}, days:{YYYY-MM-DD:{n,k,p,f,c}}}` — только итоги дня и норма на тот день (`n`), последние 120 дней, без продуктов. Тренер получает его в `GET /v1/coach/clients/:id` вместе с `plan` и `cnorm`.

**Корректировка нормы.** `POST /v1/coach/clients/:id/norm {adj}` — сдвиг в ккал, целое, кратно 10, не более ±500. Пишет документ `cnorm` (только тренер, клиент записать его не может), создаёт событие `coach.norm`. Клиент получает значение и в событии, и в ответе `/v1/sync` (`cnorm`), кладёт в `set.cnorm`; дневник питания пересчитывает норму (`base + adj`, минимум 800 ккал), белки/жиры/углеводы пересчитывает сам. При разрыве связи корректировка снимается.

**Рейтинг 0–100 (за 14 дней).** 60% тренировки + 40% питание; без дневника питания считаются только тренировки.
- Тренировки: сумма выполнения всех тренировок (100% = по плану) / плановое число за 2 недели (`plan.days` × 2, по умолчанию 3 в неделю).
- Питание, каждый прошедший день с первого дня ведения: 70% калории + 30% белок. Калории: 90–102% нормы дня = 1; перебор падает до 0 при +32%, недобор до 0 при 50% нормы (при 1500 ккал 1350 — нижняя граница). Белок: ≥90% нормы = 1. День без записи = 0. Сегодняшний день не считается.
- Цвет: ≥80 зелёный, 55–79 жёлтый, ниже красный.

**Экран.** Список: карточка = имя, дата последней тренировки, рейтинг /100, 7 засечек недели пн–вс, динамика веса, дискомфорт и число заметок. Клиент: «Общий» (рейтинг с разбором, показатели, тренировок в неделю против плана, активность, калории с нормой, вес), «Тренировки» (выбор тренировки и упражнения, график веса/повторов/объёма, выполнение плана по неделям, выполнение по тренировкам, таблица по неделям с горизонтальным скроллом, календарь и неделя с разбором дня: заметки, дискомфорт, рекорды, заметки клиента, история), «Питание» (норма и корректировка, соблюдение, неделя столбцами с пунктиром нормы, месяц кольцами: зелёное — доля нормы, оранжевое внешнее — перебор).

**Тесты.** `test/run.js`: 83 проверки (добавлены: итоги питания тренеру, запрет записи `cnorm` клиентом, шаг и предел корректировки, чужой клиент, событие и значение у клиента).


## 17. Отправка программ и тренировок клиенту

Промокодов на отдельные программы нет. Связь тренер–клиент одна: код тренера (раздел 3–4), после ввода клиент попадает в дашборд (тренировки, питание, статистика).

Программы и тренировки создаются у тренера в «Мои» и уходят клиенту двумя путями (транспорт один: `POST /v1/coach/clients/:id/programs`, событие `coach.program`, либо в демо без сервера только локальная запись):
1. **«Мои» → меню ⋯ программы или тренировки → «Отправить клиенту».** Выбор одного или нескольких клиентов. Отправляется копия без истории выполнения.
2. **Дашборд → клиент → «Тренировки» → «Назначить клиенту».** «Из моих программ» (готовая программа или одна тренировка); «Собрать из готовых тренировок» (название + тренировки из разных программ в нужном порядке → свободная программа); «Создать с нуля» (одна тренировка или программа из нескольких в конструкторе). Созданное остаётся у тренера в «Мои» («Для: Имя» или отдельная программа с пометкой «для клиента»), после выхода из конструктора предлагается отправить.

У клиента в «Мои»: программа помечена «прислана тренером», одиночные тренировки лежат в «От тренера». Все отправки видны в карточке «Отправлено клиенту».

## 18. Push-уведомления (Web Push)

**Кому и о чём**
- Тренеру: клиент завершил тренировку (pct > 0, дата не старше вчерашней по Москве). Пропуск (0%), догрузка старой истории при привязке, заметки клиента, правки профиля и питания уведомлений не вызывают. Несколько тренировок за один синк сливаются в одно уведомление; `tag` = `s-<clientId>` заменяет предыдущее.
- Клиенту: тренер прислал программу или тренировку; тренер написал комментарий (заметка, в том числе привязанная к тренировке через `ref`). Корректировка нормы калорий пуш не отправляет (только событие и запись в ленте).

**Сервер**
- Таблица `push_subs(endpoint PK, user_id, p256dh, auth)`, не больше 5 подписок на человека, мёртвые (404/410) удаляются при отправке.
- `GET /v1/push/key` (без входа) → `{key}`; `POST /v1/push/subscribe {endpoint, keys}`; `POST /v1/push/unsubscribe {endpoint?}`; `POST /v1/push/test` (5 раз за 10 мин).
- Защита от SSRF: адрес подписки принимается только https и только у известных push-сервисов (FCM, Mozilla, Apple, Windows).
- Ключи VAPID: переменные `VAPID_PUBLIC`, `VAPID_PRIVATE`, `VAPID_SUBJECT`. Без них push выключен, всё остальное работает как раньше. В `dev.js` зашиты тестовые ключи, для продакшена сгенерировать свои (`npx web-push generate-vapid-keys`).
- Событие `client.session {clientId, name, sessions:[{id,d,wn,pct}]}` уходит тренеру по сокету всегда, push поверх него.
- Содержимое пуша: имя клиента, название тренировки, процент; шифруется по стандарту Web Push, push-сервис (Apple/Google) видит только факт и размер сообщения.

**Приложение**
- Воркер `sw.js`: `push` всегда показывает уведомление (требование iOS); `notificationclick` фокусирует открытое окно и шлёт `push-open`, а если приложение закрыто, открывает `./?push=session&cid&d&sid`.
- Переход тренера: Клиенты → клиент → вкладка «Тренировки» → день тренировки, нужная тренировка подсвечена зелёной рамкой. Клиенту: программа открывает «Мои», комментарий открывает Главную.
- Профиль → «Связь с тренером»: переключатель «Push-уведомления» (только при подключённом сервере и для тренера или клиента с тренером), кнопка «Проверить». Состояния: включено, выключено, запрещено в настройках телефона, нужно добавить на экран «Домой» (iOS), браузер не поддерживает, сервер без ключей, ошибка.
- Если push не включён, тренеру приходит баннер внутри приложения (по сокету), нажатие ведёт туда же.
- iOS: push работают только у приложения, добавленного на экран «Домой» (iOS 16.4+), разрешение запрашивается по нажатию на переключатель.

**Не проверено:** реальная доставка через Apple/Google (в тестах подставной отправитель, воркер проверен отдельно), запрос разрешения на iPhone.

## 19. Боевое развёртывание

- Репозиторий приложения содержит `server/` (сервер) и `deploy/` (Docker Compose, Caddy, скрипты). Один домен: Caddy отдаёт приложение (PWA) и проксирует `/v1/*` и `/health` на сервер, поэтому CORS не нужен; `ALLOWED_ORIGINS` ограничивает остальные адреса.
- Состав: PostgreSQL 16 (том `dbdata`), api (Node 22), web (Caddy, автоматический HTTPS), backup (pg_dump раз в сутки, 14 дней).
- Установка: `deploy/setup.sh <домен> <почта>` (проверка DNS, Docker, секреты SECRET/пароль БД/VAPID, запуск, проверка `/health`). Обновление: `update.sh`. Код тренера: `coach-code.sh`. Восстановление: `restore.sh`.
- Приложение на любом домене, кроме localhost и github.io, само подключается к серверу на своём адресе (`fnet.api` = `location.origin`); на github.io остаётся режим без сервера.
- Сервер остановка по SIGTERM, `/health` проверяет базу, обрыв соединения с базой не роняет процесс.
- Тесты проходят на PGlite и на настоящем PostgreSQL 16 (`TEST_DATABASE_URL=postgres://... node test/run.js`): 99 проверок.
- Не проверено: сборка Docker-образов и установка на реальной машине (в рабочей среде нет Docker-демона), выпуск сертификата.
